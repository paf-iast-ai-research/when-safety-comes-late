# Evidence for the decisions of docs/DECISIONS.md

This file keeps, verbatim, the reasoning behind every decision in `docs/DECISIONS.md`, so that each answer can be checked against its sources.
It was produced on 2026-10-02 by a structured decision process run with AI agents (Claude) at the pilot owner's request:
a *decider* read the question, the registered text, the cited sources and the code, and proposed an answer; an *adversarial critic*
tried to refute it; where the result was not yet of high confidence an *independent judge* re-derived it; the coordinator settled the
remaining disagreements (noted below). None of this replaces the group's ratification: the answers become amendments only when the
group approves them and enters them in Table 9.1.

"prereg L<n>" or "L<n>" cites the plain-text export of the registered document (`prereg/Preregistration.pdf`) used during the decision,
one line per paragraph or table row; search the quoted words in the PDF to find the passage. File and line references point to the
code as it was read during the decision and may have moved since.

## Study A training and run gates

### Q-rounding (starred: a PENDING key)

- Final answer: Constrained-steps-matched arms at N = 0.10 and 0.25: the exact onset N·T/(1−N) is rounded to the nearest whole 20,000-step epoch, and the run then trains exactly T = 10,000,000 constrained steps. N = 0.10: onset 1,120,000 (epoch 56), total 11,120,000. N = 0.25: onset 3,340,000 (epoch 167), total 13,340,000. The realised onset fractions are 0.1007 and 0.2504. The arms keep their registered labels N = 0.10 and 0.25 in every analysis, so the H1 Spearman trend uses the registered levels. N = 0.50 is exact (onset 10,000,000, total 20,000,000).
- Outcome: ADOPT (critic: CONFIRM); confidence: high

**Decider's reasoning.** Table 2.4 'Constrained-steps matched' (prereg L317) first defines the control: 'every arm trains under the constraint for T steps'. The clause 'a late arm's total is T/(1−N)' is a consequence of that definition. Under criterion 1 the defining clause wins, so exactly T constrained steps are kept. T/(1−N) = 11,111,111.1 and 13,333,333.3 are not whole epochs. The multiplier updates once per epoch of 20,000 steps (Table 3.1 L334, L336), so the onset must fall on an epoch boundary. Rounding to the nearest epoch gives the smallest onset error: 8,889 and 6,667 steps, against 11,111 and 13,333 steps for the floor. Code check: pilot/manifest.py onset_schedule (L389-426) computes exact_onset = n·T/(1−n), rounds it to the nearest epoch (exact halves are refused), returns onset + T as the total, and attaches 'Q-rounding'. envs/onset.py _check_registered_design (L440-462) accepts only those values. A per-arm epoch length would break the registered 20,000 steps per epoch. The same onset step serves as 'N·T' for the ramp (Q-ramp-step) and for the manipulation point (Q-manipulation-point).

**Alternatives considered.** Floor the onset (1,100,000 / 3,320,000): a larger error. Round the total and set the onset to N × total: the onset is still not a whole epoch. A variable epoch length: contradicts Table 3.1's 20,000 steps per epoch. Keep the total at T/(1−N) and give up exactly T constrained steps: breaks the defining clause.

**Critic's argument (CONFIRM).** I re-read prereg L317 ('every arm trains under the constraint for T steps; a late arm's total is T/(1 − N)') and L334/L336 (500 epochs of 20,000 steps). I also re-read pilot/manifest.py onset_schedule (L389-426) and envs/onset.py _check_registered_design (L440-462 of the file; L1-30 of the persisted tail). The arithmetic holds. 1,111,111.1/20,000 = 55.56, which rounds to 56; 3,333,333.3/20,000 = 166.67, which rounds to 167. The totals are onset + T. The alternative the decider lists, rounding the TOTAL to the nearest epoch and keeping T constrained steps, gives the same numbers (555.56 → 556 epochs, 666.67 → 667 epochs). So the result does not depend on which of the two natural rounding conventions is used, which is a further argument for it. I considered a worse alternative: rounding the onset to the 200,000-step checkpoint grid (1.2M / 3.4M) so that the totals sit on the grid. It would put an onset error of up to 88,889 steps into the registered manipulation only to simplify checkpoint selection, and Q-selection-window already handles off-grid totals (contracts.extra_checkpoint_steps saves the end-relative window). Nearest-epoch rounding is the best-founded choice.

### Q-cost-critic (starred: a PENDING key)

- Final answer: Both critics (reward and cost) train from the first epoch in every Study A run (OmniSafe use_cost: True). At onset only two things change: the actor's surrogate switches from A_R to equation (3), and the multiplier starts to update (equation 4). Before onset the cost critic is trained and the cost advantage is computed, but it does not enter the actor's loss.
- Outcome: ADOPT (critic: CONFIRM); confidence: high

**Decider's reasoning.** Table 2.1 'Constraint onset' (L285) lists exactly two things that start at onset: 'the cost term enters the surrogate objective (equation 3) and the multiplier begins to update (equation 4)'. It adds that 'Before onset the cost advantage is not computed into the loss'. That wording presumes the cost advantage exists and is simply left out of the loss, so cost-critic training is not among the things onset switches on. Freezing the cost critic until onset would add a third change at onset: the late arm would start its constrained phase with an untrained A_C, while the N = 0 arm has a trained one. That confound would inflate the onset transient and bias H1/H4 (criterion 3, symmetry). It would also change OmniSafe's default use_cost: True (Table 3.1 L334: every remaining hyperparameter is the default). Training the cost critic before onset leaves the pre-onset actor trajectory unchanged: it consumes no random numbers, and the minibatch shuffle is shared. Table 2.3 (L300) logs the critics separately from the start. Code check: envs/onset.py OnsetMixin._update (L829-858). Before onset it calls super(self._LAGRANGIAN_BASE, self)._update(), i.e. PolicyGradient._update, which updates the reward critic and, under use_cost, the cost critic (policy_gradient.py:369-372). _compute_adv_surrogate (L880-887) returns adv_r before onset. check_training_config (L697-698) refuses use_cost != True.

**Alternatives considered.** Freeze or skip the cost critic until onset (use_cost False before onset): adds a confound at onset and departs from OmniSafe's default.

**Critic's argument (CONFIRM).** Verified the following. Prereg L285 lists two onset changes and says the cost advantage is 'not computed into the loss', which presumes it exists. OmniSafe PolicyGradient._update (policy_gradient.py ~L369-372) interleaves _update_reward_critic, _update_cost_critic (only under use_cost) and _update_actor per minibatch. The cost-critic step draws no random numbers and does not touch the actor's loss before onset, because OnsetMixin._compute_adv_surrogate returns adv_r while _constraint_active is False. Before onset, OnsetMixin._update calls super(self._LAGRANGIAN_BASE, self)._update(); for both PPOLag and CPPOPID that resolves to PolicyGradient._update, since PPO defines no _update. check_training_config refuses use_cost != True. I found no better reading. A frozen cost critic would add a third change at onset and an untrained A_C to the late arm only, which violates symmetry with the N = 0 arm.

The gloss of J_C in Part 2.5 ('the mean episode cost of the current epoch') is corrected by amendment to this definition.

The words do not define a different estimator, so the registered numbers, the benchmark comparison (Table 3.5) and the controller dynamics that H4 studies stay those of the cited software. The eq. Table 3.1 (L334) registers the algorithm 'as implemented in OmniSafe', Table A.1 verifies against its source, and the benchmark values that ground d_loose and G1 (Table 3.5) were produced with this window. ### Q-ramp-step (starred: a PENDING key)

- Final answer: The multiplier update of epoch e (0-based) evaluates equation (5) at t = e × 20,000, the first step of the epoch whose data the update uses. N·T in eq. (5) is the run's own onset step (the rounded onset for constrained-steps arms, Q-rounding). W = 1,000,000 steps (0.10 × the registered T = 10,000,000) in every ramp arm, whatever its total. The onset epoch's update therefore uses d_loose. The following 49 updates fall linearly. Every update from onset + 1,000,000 steps uses d = 25. Only the budget in the multiplier update changes; the surrogate has no budget.
- Outcome: ADOPT (critic: CONFIRM); confidence: high

**Decider's reasoning.** Eq. (5) (L71) gives d_eff(t) = d_loose − (d_loose − d)(t − NT)/W for NT ≤ t < NT + W, then d. Table 2.1 'Linear ramp' (L288): 'From onset the effective budget in the multiplier update falls linearly from d_loose to d over a window W = 0.10 T'. Evaluating at t = eE uses the same convention that defines which epoch is the first constrained one (Q-onset-epoch: epoch e is constrained iff eE ≥ onset). The first constrained update therefore uses exactly d_loose ('falls ... from d_loose'). The window covers the 50 epochs whose first step lies in [NT, NT+W), matching eq. (5)'s half-open domain. t = (e+1)E would never use d_loose and would reach d one epoch early. T is the registered 10,000,000 (Table 3.1 L336; Table 8.2 L410 'W 0.10 T'). A window scaled to each run's total would make the ramp shape differ between the two step-matching controls and break H2's abrupt-vs-ramp contrast across controls. For constrained-steps arms the onset is NT/(1−N), not N × 10M, so 'N·T' must mean the run's onset step for the ramp to start 'from onset'. Code check: envs/onset.py effective_budget (L213-234) and OnsetMixin._update (L840-846) call effective_budget(epoch·E, onset_step=onset_cfgs.onset_step, window_steps=R.RAMP_WINDOW_STEPS = 1,000,000) and set Lagrange.cost_limit, which compute_lambda_loss reads (lagrange.py:112). build_onset_cfgs (L379-383) enforces the registered d_loose and W.

**Alternatives considered.** t = (e+1)E, the step count when the update runs (never uses d_loose). t = (e+0.5)E. W = 0.10 × each run's total (2,000,000 for the 20M arm).

**Critic's argument (CONFIRM).** Checked effective_budget (envs/onset.py L213-234) and OnsetMixin._update (persisted L360-377). _update calls effective_budget(epoch·E, onset_step, cost_limit, d_loose, window) and sets lagrange.cost_limit, which Lagrange.compute_lambda_loss reads (lagrange.py L112). With t = eE the onset epoch k0 gets d_loose exactly. Epochs k0+1 … k0+49 get d_loose − (d_loose − d)·j/50, and epoch k0+50 (t = NT + W) gets d. That is 50 ramp updates over the half-open window of eq. (5), consistent with Q-onset-epoch's convention (e constrained iff eE ≥ onset). build_onset_cfgs enforces d_loose = R.D_LOOSE[task] and W = R.RAMP_WINDOW_STEPS. A fixed W keeps the ramp shape identical across the two step-matching controls, which the H2 contrast needs; T in 'W = 0.10 T' is Table 3.1's T. No inconsistency with the other keys.

### Q-warm-start (starred: a PENDING key)

- Final answer: Only the multiplier value is copied, with a fresh (never-stepped) Adam state. The value is the one the N = 0 run of the same task and seed logged in progress.csv after the update of epoch onset/E − 1, i.e. the value it had reached at the onset step; it is cross-checked against that run's checkpoint when one exists. It is set before the onset epoch's multiplier update. A replacement seed whose N = 0 run the N = 0 arm never received gets an auxiliary N = 0 run of that seed (`schedule resolve RUN add-auxiliary`), which is left out of the N = 0 arm by the matching and the analysis. Added rule: if the N = 0 run a warm-started run depends on (an auxiliary run included) is excluded under Part 5.6, no value is taken from the excluded run. The scheduler launches a warm-started run only after its dependency has finished training, so that warm-started run is a blocked run that never trained. It is not excluded: it is superseded by its arm's next unused seed (`schedule resolve RUN replace`), whose source is the N = 0 arm's run of that seed or, failing that, an auxiliary run. An excluded auxiliary run is never repeated or replaced itself.
- Outcome: ADOPT_MODIFIED (critic: CONFIRM_WITH_EDIT); confidence: high

Setting it before the warm-started run's update of epoch k0 aligns the two runs. 'Same seed' forces an auxiliary run when a replacement seed has no N = 0 partner. Keeping the auxiliary run out of the N = 0 arm keeps that arm's registered seed list (Part 5.5/5.6). For the added rule: an excluded run must not supply data, and Part 5.6 repeats an excluded run with the next unused seed. When the N = 0 seed-s run is excluded, the N = 0 arm moves to seed 5, and replacing the warm-started seed-s run with its own next unused seed (also 5) keeps both arms on the same seeds without an auxiliary run. For an excluded source run, use its logged value when its record reaches the onset step: reuses an excluded run's data.

### Q-rate-limit (starred: a PENDING key)

- Final answer: The rate-limited multiplier runs OmniSafe's own update unchanged (Adam, lr 0.035, on −λ(J_C − d), clamped to [0, upper bound]). After each such step the result is clipped to [old − b, old + b] with b = 0.05 × old + 0.01, where old is the value before that epoch's update. It is then clamped at 0. Adam's moments are not altered by the clip. The proposed (pre-clip) value is logged each epoch as Onset/MultiplierProposed, and the report gives the share of constrained epochs in which the clip bound. Adam's step is about its learning rate (0.035) while the sign and size of J_C − d are steady, so the clip then binds only while λ is below about 0.5. Adam's step reaches about 2.5–3 × 0.035 after a sudden rise in the violation, and the clip also binds then at larger λ. The amendment states this, and the rate-limited arm stays the secondary H4 check, as registered.
- Outcome: ADOPT (critic: CONFIRM_WITH_EDIT); confidence: high

**Decider's reasoning.** Table 2.4 (L313): 'Each multiplier update is clipped so that the multiplier changes by at most 5 percent of its current value plus 0.01 per epoch' (numbers registered as a decision, Table 8.2 L416). The update being clipped is the registered one: OmniSafe's, through its configured optimiser (eq. 4 text L69; Q-multiplier-adam). Clipping the applied change after that update is the literal reading. 'Its current value' at the time of the update is the value before it. The gradient fed to Adam is −(J_C − d) whatever the clip does, so leaving the moments untouched is the only consistent choice: altering them would invent a second change not in the text. Replacing Adam by the SGD form of eq. (4) to make the clip bind more would change the registered algorithm (Table 3.1 L334, 'as implemented in OmniSafe'). The registered rate stays as it is. H4's primary variant is the warm start (L239), so the weak binding of the rate limit does not touch a confirmatory claim; logging the proposed value makes the binding visible. Code check: envs/onset.py rate_limit (L237-251) and RateLimitedLagrange.update_lagrange_multiplier (L610-617): super().update (lagrange.py:129-136), record last_proposed, clip with relative·|old| + absolute, clamp to [0, upper]; installed in OnsetMixin._init (L808-814).

**Alternatives considered.** Replace Adam with the SGD form of eq. (4) and clip it: changes the registered optimiser. Feed the clipped step back into Adam's moments: not defined by the text. Read 'current value' as the post-update value: circular.

**Critic's argument (CONFIRM_WITH_EDIT).** The decision is correct. RateLimitedLagrange.update_lagrange_multiplier (persisted onset.py L141-148) calls OmniSafe's update (lagrange.py L129-136), records last_proposed, applies rate_limit(old, proposed, …) with relative·|old| + absolute, and clamps to [0, upper]. PPOLag._update then logs the clipped value and the surrogate uses it. Reading 'its current value' as the pre-update value is the only non-circular choice, and leaving Adam's moments untouched is right. One factual claim in the answer, which goes into the amendment, is too strong: 'Under Adam the clip binds only while λ is below about 0.5'. That is true only when Adam's step ≈ lr. I ran Adam(lr = 0.035) on the loss −λ·g in the pinned torch 2.14: after 200 epochs at g = 1, a jump to g = 60 gave steps of 0.053, 0.067, 0.077, 0.084, 0.089. Adam's asymptotic bound is (1 − β1)/sqrt(1 − β2) ≈ 3.16 × lr. After g turned negative, λ kept rising by 0.079, 0.069, … (momentum). In this study J_C − d jumps at onset and after, so the clip can bind at λ up to about 1.5–2. The revised text states the condition correctly. Logging Onset/MultiplierProposed makes the actual binding visible either way.

### Q-reset-injection (starred: a PENDING key)

- Final answer: Both interventions act on the actor's last two layers: the output layer and the hidden layer before it (actor.mean[2] and mean[4]). log_std is a free parameter, not a layer: it is neither reset nor frozen, and it keeps training with its Adam state. Reset overwrites those layers in place, then removes their Adam state (optimizer.state.pop). Injection works as follows. The old head is frozen. A fresh head θ'1 (trained) and its identical frozen copy θ'2 are added. The output is frozen(z) + (new(z) − new_frozen(z)), bit-identical at injection. The first hidden layer (trunk) and log_std keep training and receive gradients through all three heads, so the number of trainable parameters is unchanged. ### Q-bootstrap-details (starred: a PENDING key)

- Final answer: Each analysis gets its own generator, numpy.random.default_rng([0, crc32(analysis id)]), recorded with the result. B = 10,000 resamples. Percentile limits use numpy's 'linear' quantile rule. When the two arms of a contrast have identical seed lists, one index draw serves both (pairs kept together). Otherwise, including partly overlapping lists, each arm is resampled on its own indices. A Spearman trend resamples seed ids from the union, each carrying all its points. Undefined resamples (a constant variable) are dropped and counted, and flagged above 1 percent. Holm (Part 5.2) uses the two-sided Welch p of a two-arm claim. For a Spearman claim (H3 (a)) it uses the bootstrap p = min(1, 2·min(#ρ* ≤ 0, #ρ* ≥ 0) / B_defined).
- Outcome: ADOPT (critic: CONFIRM); confidence: high

Joint resampling of identical seed lists is exactly that sentence (paired seeds of Part 5.1, L124). With different lists, the standard two-sample bootstrap resamples each arm on its own indices, which is unbiased and needs no ad hoc handling of seeds missing from one arm. Part 5.4 (L130) explicitly requires the trend resample to carry 'all of a seed's factor levels together', and the union resampling does this. A generator seeded by the analysis id makes every interval reproducible and independent of the order in which analyses run, and it is fixed before data (no forking). The linear quantile rule is numpy's default, and with B = 10,000 the choice of rule is immaterial. Part 5.4 registers only a percentile interval for a correlation.
